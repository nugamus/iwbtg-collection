# The client: Storage

Part of [the client](../client.md).

Storage (`storage.rs`, #473): the one place the client keeps things between sessions, so no other module uses `cfg` for it. `Store::config()` (the settings file, with the bindings in its `[bindings]` table) and `Store::data()` (save slots, `saves/<game id>.save`, the local stats, `stats.toml`, and replays, `replays/...`) return a store, or `None` when there is nowhere to keep things; a store reads, writes and removes bytes or text by a `/`-separated name, and every failure is an error string the caller turns into `storage::warn` while the game keeps running. Natively a store is a folder (config: as in Settings; data: `iwbtg-collection` in `%LOCALAPPDATA%` on Windows, else `$XDG_DATA_HOME` or `~/.local/share`), and a write goes to `<name>.tmp` beside the file and is renamed over it, so a crash never leaves half a file; warnings go to stderr. On the web (`wasm32-unknown-unknown`) a store is the browser's `localStorage`, one entry per name under the key `iwbtg-collection/config/<name>` or `iwbtg-collection/data/<name>`; text is stored as is (the settings TOML stays readable in the browser's dev tools) and bytes as lowercase hex (a save slot is a few dozen bytes, far below the quota). Private browsing or a blocked site (no `localStorage`) is one console warning when the store opens, and the session then runs without keeping anything; a full quota on a write is a console warning and the next change tries again. The web build runs the same store in a browser ([Web](web.md), #29), so a reload keeps progress and controls.

Where things are kept (#107; `backend::root` picks the folder and the `native_folders_per_os` test pins it). An empty variable counts as unset; with neither the variables nor `HOME` there is no store and nothing is kept.

A save file is a postcard envelope (`savefile::SaveFile`, version 3, #1150): a format version, the **package id** and built-in revision (`engine_rev`) that wrote it, and a `save::Checkpoint` payload — the same versioned encoding a replay's `FromSave` carries. The checkpoint names the room by its stable **package name** (`RoomKey`) and records the ruleset/profile, the position precision, the saved position, facing/flip and counters, and the save object's stable key (`Checkpoint.point`): `name:<declared name>` for a named placed instance, else `at:<room>/<kind>@<xbits>,<ybits>` from its exact spawn position. The key is resolved against the room data on load; a point that moved, was removed or was renamed is refused with the same one-warning new-game path, never a different instance. The name is resolved to the package's current `RoomId` on load, so adding, removing elsewhere or reordering rooms does not move a save into another room (adding the showcase's boot room did, #1140/#1144), and a save in a room that is not `role = "play"` (the boot room) or a room the package no longer has is refused. The package id and built-in revision are the compatibility check: a save from another package or another built-in revision is refused rather than resumed under rules it was not written for. A cosmetic or unrelated-room update changes neither, so it keeps the save; the envelope does not compare a whole-package `gameplay_hash`, which a room insert would change (#1019). The version 2 envelope (#1019) and version 1 (#1145) migrate on read; neither recorded the precision, so the migration infers it from the saved room's physics profile (the stored position was already quantized, so the inference only labels it). A file that does not parse as a versioned envelope, such as an older build's raw slot, is one warning and a new game, and its bytes are copied beside it as `<name>.old` so they stay recoverable. No refusal is a silent resume. The envelope and the checkpoint it holds are decoded exactly: bytes after the payload are refused, so an appended or unknown field is never silently ignored. The checkpoint is resolved through `Checkpoint::to_slot`, which runs the same `Checkpoint::validate` as the replay's `FromSave`, so a checkpoint with a format this build does not read is refused identically on both paths (#1325).

`$IWBTG_CONFIG_DIR` replaces the whole config folder (no `iwbtg-collection` is added); tests and checks use it. macOS uses the Linux folders rather than `~/Library/Application Support`, so one rule covers both. Settings survive a restart because every change is written through the config store at once (`settings::update`; `settings::tests::file_write_and_read` reads back what it wrote).

A player never sees stderr or the browser console, so `storage::warn` also posts a notice (`ui::notice`, [UI](ui.md), #566): the first storage warning of a session shows a short card in the bottom left, "Not saved: Saves and settings may not be kept this session.", for 6 s; later ones only go to the console. The card does not show the message itself (file names and OS errors), which stays in the console line. On the web the private-browsing warning at store open goes through `warn` too, so it shows the card.
