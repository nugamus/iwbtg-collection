# The client: The window and the view

Part of [the client](../client.md).

`cargo run -p iwbtg-client -- <package folder or .iwbz> | --select <folder> [--trace-mode] [--fps <N|unlimited>] [--interpolate] [--bind ACTION=INPUT] [--show-bindings]` opens a package in a window (Bevy 0.20, 2D rendering, windowing, audio, gamepads and bevy_ui with picking and the headless widgets; 3D features are off until they are needed, because they pull system libraries). `--select <folder>` starts on a placeholder list of the folder's packages instead, and quitting a game goes back to it ([shell](shell.md)). `--ui-gallery` opens the [UI](ui.md) gallery instead. `package.rs` opens the folder like `iwbtg pkg check` does (engine pack bundled from `../_engines`, strict load), or an `.iwbz` file ([import](import.md)) and prints the errors of a broken package. `view.rs` owns the `sim::Sim` as a non-send resource (the script host is not `Send`) and draws every visible instance that has a sprite, one Bevy sprite each, using the image of its `SpriteId`, a strip or, with `columns`, a grid read row by row (the frame is found from the image width; `iwbtg_format::sprites::sprite_pngs` gives the order), its origin, frame (the sim's `Image::subimage`, R7c), scale, angle and alpha, at the position the sim reports, in the sim's draw order. Draw order is never a float of the depth (#789): `view/order.rs` takes the sim's own list (`iwbtg_sim::events::draw_order`: alive, active, visible, depth descending, then creation) and turns each place in it into a z, so the client and the sim cannot disagree and ids or large depths (GM overlays use -1000000) cannot reorder equal-depth instances. `view/order.rs` declares the room's layers back to front: the room colour, the background layers in file order, the world band, then the foreground layers in file order (`order::Layer`, one stable tie rule: a later background or foreground draws on top). `art.rs` asks that model for every z instead of defining its own constants, so tiles and backgrounds are layer entries. The sign text box and the countdown are `order::Hud` slots at z 996 and 997: above the room colour, backgrounds, the world band and foregrounds (GM allows at most 8 background slots, so the top foreground stays below 996) and below the hitboxes (998), so a room's art can never cover them. Instances and tiles share the world band, z -990 to 990: the room's tile layers (`order::Ladder`, filled by the room art) sit at fixed, evenly spaced z in draw order (equal depths in file order), and the instances between two layers by depth share the gap between them, evenly by their place in the list; a tile layer at an instance's own depth draws over it (OpenGMK's picture, CLONE_SPEC TR-ROOM-13, partial). The results' room picture places a room's placed instances the same way. The room is letterboxed to fit the window and drawn with nearest-neighbor filtering. The runner follow that decides view 0 is `iwbtg_sim::view::Camera`, an explicit preset (target, dead zone, room clamp, smoothing) built from the room's view each tick with one pure `step`: the same arithmetic is testable on its own, the view stays the hashed state, and the client only reads the resulting view. The sim ticks on Bevy's fixed clock (`Time<Fixed>`, set to the game's `tick_rate`, 50 for the IWBTG games), so the tick rate does not depend on the frame rate; a slow frame runs several ticks, a fast one none (Bevy clamps one frame's catch-up to 250 ms, so after a long stall the sim slows down instead of racing). Each tick takes one `InputFrame` from `input.rs`, whose collector keeps per-input edges (keys and controller) between ticks. `bindings.rs` holds the one global binding set: the IWBTG default keys (arrows, Shift jump, Z shoot, R restart, Q suicide, S skip, Enter accept, P pause, M mute, F2 reset) and default controller inputs (D-pad or left stick move, A jump, X shoot, Y restart, B suicide). Escape and Start are the client's pause key and button (`pause::PAUSE_KEY`, `pause::PAUSE_PAD`, [pause menu](pause.md); #758, #624), so the game's `menu` action has no default at all (the sim's `IWBTG_DEFAULT_KEYS` still maps Escape to `menu` for the research `.inputs` files; the client drops that one key) and Escape sends the game nothing; `--bind menu=<key>` or `--bind menu=pad:<name>` gives it one, but not Escape or Start: binding any action or client key to the pause key or button is refused (#761). Changes are saved with `--bind ACTION=INPUT[,INPUT...]` (a key name or `pad:<name>`, e.g. `--bind jump=Space,pad:select`) in the `[bindings]` table of the settings file (`[bindings.keys]` and `[bindings.pad]`, action name to a list of input names; Settings), so the same code works natively and in the browser; `--show-bindings` prints them. A broken entry (unknown action or input, wrong type, a key bound twice) is a warning and that action keeps its default. A `bindings.toml` left by an earlier build is moved into the settings once, when `[bindings]` is empty, and then removed (a broken one stays and warns); the old `--bindings-file` flag is gone. An action named in the file loses its default keys (or controller inputs); a double binding is an error. `quick-retry` sits in the same tables (key Backquote by default, no controller input), as do `skip-cutscene` (Backspace) and `frame-advance` (F); each is a client key, not an `Action`: the collector only raises a flag for `retry.rs`, so it never enters an `InputFrame` or a replay, and it may not share an input with an action. No rebinding screen yet (menus are later). Only the active controller counts (the one that last had a button pressed), and a stick axis counts only after it has been seen near the centre (press above 0.6, release below 0.3), so a device with a resting axis, such as a DualSense's motion sensors over Bluetooth, cannot hold a direction. That rule is `input::PadReader`, which reads Bevy's `Gamepad` components and is the same on native and web (#474): in the wasm32 build the `bevy_gilrs` feature already uses gilrs's browser backend, which polls the Gamepad API (`navigator.getGamepads()`) each frame and fills the same components, with stick Y flipped to point up as on native, so bindings, the stick gate and the active-pad rule need no web code. Browser limits: a page sees a controller only after one of its buttons is pressed while the page is open (which is also when it becomes active), the API needs a secure context (`localhost` and `127.0.0.1` count; a plain-HTTP LAN address does not), and buttons follow the browser's standard layout (`mapping == "standard"`, as Chrome and Edge report for common pads; for a pad the browser does not map, gilrs reads its raw button indices as if they were the standard layout, with no SDL mapping database as on native, so its buttons may land on the wrong inputs). For such a pad the web build tells the player instead of guessing a layout (#717): `input::watch_unmapped_pads`, started in the wasm32 `main`, listens for the browser's `gamepadconnected` event and, when the pad's `mapping` is not `standard`, writes its id to the browser console and posts a notice once per session (`Kind::Pad`, [UI](ui.md)) saying the browser may mix up its buttons and that Chrome or Edge map most controllers. There is no built-in mapping table: raw button indices differ by browser and OS, and no well-sourced table exists for them. Rebinding is not the advice yet, because the web build has no command line and no rebinding screen; once the settings' controls panel exists, the notice can point there. The web build's page opens a package over HTTP ([Web](web.md), #29), so this same pad path runs in a browser. The F3 overlay's last line shows the actions the last tick saw and the controller inputs that are down. Frames draw the state the last tick left, with no interpolation by default (the originals draw every step, so a frame between two ticks would show something the game never had). `--interpolate` is an option for fast displays: each frame draws every instance that way between its position before the last tick and its position after it, by how far the fixed clock is into the next tick; an instance that moved more than 32 px in one tick, a new instance, and any instance after a room change is drawn at its new place at once. It changes only the picture, never the sim. The sim's `RoomOutput::Transition { kind, steps }` is consumed into a client `view::transition::Transition` resource: a wall-clock `Playing` at a declared 10 ms per step (the measured 30-step transition took 278 ms), the `Out`/`In` phase, progress and the input policy each phase declares. This slice only records it: nothing draws or gates input from it yet, so the room change stays instant and the picture is unchanged; E4b (#1247) draws the fade and enforces the policy behind the ruleset value, and `gm8` keeps today's behavior. The frame cap (`--fps`, default 60, or `unlimited`) is a sleep-and-spin limiter at the end of each frame; vsync is off. The F3 debug overlay (ticks and frames per second, the tick, the room, the kid, the input) is its own module, [Overlay](overlay.md); `view::Stats` counts the ticks it shows. A halted sim stays on screen with its error in the overlay. After every tick `follow_room_speed` reads the sim's `room_speed` (a room's file speed on entry, or what the game set) and retunes `Time<Fixed>` to it, clamped to 1 to 1000 ticks per second and times `view::ClockSpeed` (1, or the slow motion speed, [practice assists](practice.md)), so a room or game that changes `room_speed` ticks at the new rate from the next tick; the overlay's `game N` shows the current rate. The `world` built-in sets `room_speed` back to the game's `tick_rate` at every room start, so in the IWBTG games it only differs where a game's own code sets it. Two things the sim reports are drawn by `view/hud.rs`: the sign text box (a white-framed black panel at the bottom of the room, shown while ticks keep sending `BuiltinOutput::TextBox`, so it goes away on the first tick without one) and the `time_limit` countdown (read from the running timer's built-in state, drawn as `H:MM:SS` in white at the timer's own position; the position is a guess, the spec only says the timer's Draw event draws text). **The showcase** (#852): `crates/client/showcase.pkg` is the one package a tester plays to see what the client does today. It has the real Kid (idle, run, jump and fall sprites and the bullet from I wanna Little Trap, credited in its `CREDITS.md`; the only fangame art in this repo, games#34); everything else is original (rooms, tiles, backgrounds, sprites, particles, music and sounds). A **boot** room is first in room order and holds no instances, as `rInit` does in the 20 games: `game_restart` enters it on R and the next boot tick loads the save, so a play room's `kid_start` cannot make a second kid (#1140). The three stages: the **courtyard** (a sign that shows its text box while the kid stands on it, a save stone to shoot, spikes, a wall that needs the double jump, drifting clouds and fireflies, the music), the **great hall** (2400 px wide with a view that follows the kid, a back wall whose windows show the sky, banners as a tile layer in front of the kid, a foreground mist layer, a hanging beam with spikes pointing down, stepping stones and two more saves) and the **summit** (snow and brazier embers as particle systems, a sea of clouds, and the gold star, the `game_clear`, on a pedestal). Each portal is a stage split (`enter_room`), the star raises `run_end`, so `--ranked` ends on the results page. The blocks are invisible instances drawn by the rooms' tile layers. The portal (24 frames, 6 a row) and the star (25 frames, 5 a row) use `columns`. Test `package::tests::the_showcase_clears_with_a_scripted_route` plays a scripted route to its clear with no death. Tests use small single-feature packages in `crates/client/tests/fixtures/` instead (`input.pkg`, `audio.pkg`, `save.pkg`, `particles.pkg` and `clear.pkg`, which can be cleared: walk right, jump the block, take the blue warp to the `goal` room, its one stage split, jump the spike and touch the gold `game_clear`; `stats::tests::the_clear_demo_clears_twice_with_a_split` plays it twice); they are placeholder rectangles, not for testers. `--screenshot <png>` saves the window after a few frames and exits, for checks. It captures at frame 90 and exits at frame 150; every frame of such a run advances time by exactly 1/60 s (`TimeUpdateStrategy::ManualDuration(SHOT_FRAME)`), not by the real frame time, so the fixed clock (sim, HUD timer, the timer running under `--pause-preview`) and the real-time animations (the loading cherry, tweens) stand at the same point in every capture: two builds of the same commit, debug or release, give 0 differing pixels with `screenshot_diff.py` (#942). Normal play keeps the real clock. When the size is known (`--window`, or the gallery's and previews' `--ratio`) the window cannot be resized or maximized and any size change from outside is undone each frame (`ShotSize`, `hold_shot_size`); a capture of another size is not saved, prints `error: screenshot is WxH px, not the WxH asked for ...` and the run exits with an error. Cause found for #861: a maximized 800x608 check on a 7680x2160 monitor at 125% scaling saved 7680x2071 (the work area less the title bar); the settings file was not involved, since a `--screenshot` run neither reads nor writes it ([settings](settings.md)). It works on the default Vulkan backend and on DirectX 12 (`WGPU_BACKEND=dx12`, which draws sprites right since [render fixes](render_fix.md), #571); Vulkan panics (`get_physical_device_surface_capabilities`, then `Fallback system failed to choose present mode`) while the display is asleep or locked, DX12 does not.
