# The client: The window and the view

Part of [the client](../client.md).

`cargo run -p iwbtg-client -- <package folder> [--trace-mode] [--fps <N|unlimited>] [--interpolate] [--bind ACTION=INPUT] [--show-bindings]` opens a package in a window (Bevy 0.20, 2D rendering, windowing, audio, gamepads and bevy_ui with picking and the headless widgets; 3D features are off until they are needed, because they pull system libraries). `--ui-gallery` opens the [UI](ui.md) gallery instead. `package.rs` opens the folder like `iwbtg pkg check` does (engine pack bundled from `../_engines`, strict load) and prints the errors of a broken package. `view.rs` owns the `sim::Sim` as a non-send resource (the script host is not `Send`) and draws every visible instance that has a sprite, one Bevy sprite each, using the image of its `SpriteId`, a strip or, with `columns`, a grid read row by row (the frame is found from the image width; `iwbtg_format::sprites::sprite_pngs` gives the order), its origin, frame, scale, angle and alpha, at the position and depth the sim reports. The room is letterboxed to fit the window and drawn with nearest-neighbor filtering. The sim ticks on Bevy's fixed clock (`Time<Fixed>`, set to the game's `tick_rate`, 50 for the IWBTG games), so the tick rate does not depend on the frame rate; a slow frame runs several ticks, a fast one none (Bevy clamps one frame's catch-up to 250 ms, so after a long stall the sim slows down instead of racing). Each tick takes one `InputFrame` from `input.rs`, whose collector keeps per-input edges (keys and controller) between ticks. `bindings.rs` holds the one global binding set: the IWBTG default keys (arrows, Shift jump, Z shoot, R restart, Q suicide, P pause, M mute, F2 reset) and default controller inputs (D-pad or left stick move, A jump, X shoot, Y restart, B suicide, Start menu). Changes are saved with `--bind ACTION=INPUT[,INPUT...]` (a key name or `pad:<name>`, e.g. `--bind jump=Space,pad:select`) in `bindings.toml` in the user's config folder (`--bindings-file` overrides); `--show-bindings` prints them. An action named in the file loses its default keys (or controller inputs); a double binding is an error. No rebinding screen yet (menus are later). Only the active controller counts (the one that last had a button pressed), and a stick axis counts only after it has been seen near the centre (press above 0.6, release below 0.3), so a device with a resting axis, such as a DualSense's motion sensors over Bluetooth, cannot hold a direction. The F3 overlay's last line shows the actions the last tick saw and the controller inputs that are down. The bindings file is still its own `bindings.toml`, not the `[bindings]` table of the settings file (Settings, Storage); moving it there, so it also works in the browser, is #541. Frames draw the state the last tick left, with no interpolation by default (the originals draw every step, so a frame between two ticks would show something the game never had). `--interpolate` is an option for fast displays: each frame draws every instance that way between its position before the last tick and its position after it, by how far the fixed clock is into the next tick; an instance that moved more than 32 px in one tick, a new instance, and any instance after a room change is drawn at its new place at once. It changes only the picture, never the sim. The frame cap (`--fps`, default 60, or `unlimited`) is a sleep-and-spin limiter at the end of each frame; vsync is off. An overlay in the top-left corner shows ticks per second, frames per second, the tick count, the room (name and size) and the kid's x, y, hspeed and vspeed (or `no kid`); F3 hides and shows it. A halted sim stays on screen with its error in the overlay. After every tick `follow_room_speed` reads the sim's `room_speed` (a room's file speed on entry, or what the game set) and retunes `Time<Fixed>` to it, clamped to 1 to 1000 ticks per second, so a room or game that changes `room_speed` ticks at the new rate from the next tick; the overlay's `game N` shows the current rate. The `world` built-in sets `room_speed` back to the game's `tick_rate` at every room start, so in the IWBTG games it only differs where a game's own code sets it. Two things the sim reports are drawn by `view/hud.rs`: the sign text box (a white-framed black panel at the bottom of the room, shown while ticks keep sending `BuiltinOutput::TextBox`, so it goes away on the first tick without one) and the `time_limit` countdown (read from the running timer's built-in state, drawn as `H:MM:SS` in white at the timer's own position; the position is a guess, the spec only says the timer's Draw event draws text). `crates/client/demo.pkg` is a small original package for trying it; `demo-grid.pkg` is the same with a four-colour 2x2 `columns` kid; `demo-hud.pkg` adds a brown sign, a 1:30 time limit and a green start zone; `demo-clear.pkg` is the one that can be cleared, and the one demo with the real Kid (idle, run, jump and fall sprites and the bullet from I wanna Little Trap, credited in its `CREDITS.md`; the only fangame art in this repo, games#34): walk right, jump the block, take the blue warp to the `goal` room (its one stage split, `enter_room`), jump the spike and touch the gold `game_clear`, which raises `run_end` (test `stats::tests::the_clear_demo_clears_twice_with_a_split` plays it twice). `--screenshot <png>` saves the window after a few frames and exits, for checks.
