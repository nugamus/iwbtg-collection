# The client: Audio

Part of [the client](../client.md).

Audio (`audio.rs`): a package's `sounds/<id>.ogg` and `music/<id>.ogg` become shared `Arc<[u8]>` handles once when it opens (`package::Package::sound_bytes`), so each run clones the handles instead of copying every OGG (#1415). Each tick's `SoundOutput` events (and a script `emit(name)`, which plays the package sound of that name) go into a queue that is played back through Bevy's audio (Ogg Vorbis only, `bevy_audio` + `vorbis`). The sim decides what plays and for how long; the client only plays, loops, stops, pauses and sets volume and pitch per voice. Every event carries the sim tick of its call, and `Play`/`Load` carry the sound's `length_ticks`; the mixer takes a tune's loop length from the event, never from the package's sound table. SuperSound volumes are hundredths of a dB and become a linear factor; DLL handles (`Load { file }`) map to the package sound with the same file stem. `--audio-offset <ms>` (0 to 500, default the saved value, else 0) holds every cue back by that long, so it moves playback only and never the sim; it is saved in the settings file. Volume: each voice plays at its own volume times the master volume times the music volume (a looping voice, or a package sound of GM kind MULTIMEDIA) or the sound volume, all percentages from `[audio]` in the settings file (default 100, linear amplitude); `--volume <0-100>` sets the master volume and is saved. A volume changed while sounds play (Settings, or the pause menu's Options) reaches them at once: `audio::apply_levels` rescales every playing voice and every voice about to start to the new levels, each voice keeping its own volume and whether it counts as music. Mute: `--mute` (this run only, not saved), the environment variable `IWBTG_MUTE` set to anything but empty or `0`, and every `--screenshot` run play no sound at all: no voice is started (a voice whose volume factor is 0 is never spawned) and Bevy's `GlobalVolume` is set to silent, with `audio muted` in the log. Agents always launch the client with `--mute` (docs/lanes/README.md). The `--ui-gallery` and `--card-preview` windows add no audio plugin and are silent. The first room's start runs inside `Sim::new`; the first `step` keeps that output (#466), so it plays with the first tick's. `shake(ticks, strength)` moves the camera by up to `strength` pixels each frame while it runs, on top of the view centre (`apply_shake` runs after `view::follow_view`) (a client effect with its own wobble, not the sim's random numbers). Music sync (docs/product.md): a looping tune with a known length (the event's `length_ticks`) carries a `MusicSync`, which turns the sim's tick count (plus the fixed clock's fraction of the next tick) into where the tune should be: ticks played over the tick rate, times the pitch, wrapped to the loop; a pause holds it and a pitch change re-anchors it. `sync_music` compares that with the sink's position every frame and seeks the tune to the expected position when it is more than 2 ticks (40 ms at 50 Hz) off, measuring the short way round the loop; smaller drift is left alone, and a tune is left alone for 10 ticks after it starts, is paused or is seeked. A lag spike therefore pulls the tune back to the beat; a stop, restart or new `play` starts a fresh voice, which is exact by construction. Sound effects are not synced.
`crates/client/showcase.pkg` has jump, double jump, shoot and death sounds and a looping 19 s tune that every room keeps playing (`music` with `every_step_if_not_playing`); the test fixture `crates/client/tests/fixtures/audio.pkg` has jump, shoot and death sounds and a short loop.

Under slow motion ([practice assists](practice.md)) every voice plays at its speed times `view::ClockSpeed` (pitch included, as the clock is slower); `MusicSync` keeps the game's own speed, since its expected position is counted in ticks, so the music stays on the slowed tick clock.

Web audio unlock (`audio/unlock.rs`, #472): a browser keeps a page's audio suspended until a key press, click or touch on the page (a controller press is no user gesture to a browser, so it does not count). `web/index.html` keeps every `AudioContext` the page makes (it wraps the constructor before the client starts), resumes them on the first `keydown`, `pointerdown` or `touchend`, and sets `window.iwbtgAudioUnlocked` once one runs; a page without that script counts as unlocked. Until then the audio module is locked (`unlock::Lock`): a looping voice that starts gets no sound voice yet, only its `MusicSync`, its settings and the sound to play (`unlock::Held`), and pause, volume and pitch commands change those settings; a one-shot sound is dropped, since it would be over by the time the sound comes on. Each frame `poll` reads the flag; when it is set, `release` gives every held tune its sound voice starting at the position `MusicSync::expected` gives for the current tick (paused if the game paused it, at the clock speed), so the first room's music comes in where the tick clock has it, and normal music sync takes over after the usual settle. A note in the top left of the notices' area (the leaderboard column in a game; with the HUD hidden, the top right of the window, clear of the F3 overlay) says `Sound off — Press a key or click to turn the sound on.` until then and fades out when the lock opens. Natively the sound is never locked; the hidden flag `--audio-locked` makes a native run start locked, opened by any key or mouse button, for tests and screenshots (with `--mute` the note still shows, and nothing plays). A silent browser run (volume 0) starts unlocked.

Music sync's drift correction is native-only: a browser tune keeps the position it started at. rodio's `Player::try_seek` blocks the caller until the audio callback answers on a channel, and cpal's WebAudio backend runs that callback on the main thread (a `setTimeout`/"ended" pull loop), so the first correction deadlocks the page ([#1127](https://github.com/nugamus/iwbtg-collection/issues/1127)); `sync_music` is a no-op there. The tune still starts where the tick clock says (the unlock release above) and follows pause and pitch; only the periodic pull-back to the beat is lost. The sustained `web_smoke.py` session plays a looping tune with input so the harness would catch a regression.
