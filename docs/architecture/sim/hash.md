# The simulation: State hash

Part of [the simulation](../sim.md).

## State hash

This is the live text moved from section 10.1 of [the sim core plan](../../plans/sim-core.md), which stays only as history; this page is the authority. The other determinism rules are on [Determinism and purity](determinism.md).

- `hash::state_hash(&World) -> [u8; 32]` is BLAKE3 over the **postcard** encoding of a canonical `HashView` struct borrowed from `World`: every field of `World` except `output`, `grid`, `room_requests`, `particle_defs` (the definition each `particle_system` system was built from, kept for the client's drawing and never read by the sim, #866) and `particle_clears` (the count of `clear` calls per such system, for the client to follow them, #883), in declaration order: tick, room, `room_tick`, room speed, instances in id order with every field, the instance list's room-entry ranks (`room_entry` and `next_entry`, research#142: they decide "the first", R21), `next_id`, run-time `var_names`, globals (both in `BTreeMap` order), engine globals, RNG state (`World::rng`, the gameplay or shared stream) and the named stream state (`World::streams`: the layout, `effects`, `draw` and `script`; #1157), `input` (this tick's frame and the direct-read latch, which changes outcomes per I1), views, pending request, persistent rooms, save slot, sound state, timing state, particle state (`World::particles`: types, systems, emitters, the live particles that still draw; #764), status, the play mode (`World::mode`, original or stripped, #561), the map (`World::map`, an index into `GameDef::maps`, #505), `setup_applied`. A field added to `World` is hashed unless it is a cache or, like `particle_defs` and `particle_clears`, a record the sim only writes and never reads. `Real` serializes its canonical bits, so every NaN hashes the same. A `Value::Array` (#984) hashes as its elements in order (postcard's length varint, then each value), so an array hashes by content, nested arrays included, and an empty array differs from `None`.
- Postcard writes lengths as varints, so wasm32 and x86_64 give the same bytes. `std::hash::Hash` and its hashers are never used for state hashing: slices write their length with `write_usize` (4 bytes on wasm32, 8 on x86_64), and `DefaultHasher`/`RandomState` are unspecified across Rust versions (both are banned in the sim).
- No `usize` in hashed state, no pointers, no hash-map order. The output queue and the broadphase grid are not hashed.
- `setup_applied` is hashed, so a trace run that used setup actions can never match a clean verification.
- Checkpoints store the first 16 bytes.
- `hash::HASH_LAYOUT` versions the encoding. Adding fields to a state struct (for example `KidGlobals`) changes the hash but not the layout: re-pin the vectors in `tests/hash_vectors.rs` and the final hash in `tests/determinism.rs`. Bump `HASH_LAYOUT` only when the encoding itself changes.
