# The simulation: Number handling

Part of [the simulation](../sim.md).

## Number handling

GM8 reals are IEEE binary64 doubles. Our sim uses f64 for every real.

- **`Real` newtype.** Every float in built-ins goes through `sim::num::Real(f64)`. If the float model ever has to change, it changes in one place.
- **Exact operations only.** `+ - * /` and `sqrt` are correctly rounded IEEE on all three targets. Rust never contracts to FMA (RFC 3514). x86_64 uses SSE2.
- **Rounding.** `num::round` is banker's rounding (`f64::round_ties_even`), which matches Delphi and GM8. It places bounding boxes and converts reals to integers where GM8 rounds. `f64::round` (half away from zero) is banned. Truncation and other conversions are named helpers (`to_int_trunc`, `to_int_round`, `frac`, `gm_mod`, `gm_div`).
- **Comparisons.** `num::gm_eq/ne/lt/le/gt/ge` and `gm_bool` take the run's `NumRules`: an epsilon of 1e-13 on the difference by default, or exact comparison (N1, N2; the recorder and the real runner both use a tolerance, its exact value is OPEN and the default is the recorder's 1e-13). Built-in code uses them wherever the spec says the original compared reals in GML. Scripts call the same functions by name ([0001](../../decisions/0001-script-language.md)).
- **Transcendental math.** `sin`, `cos`, `atan2`, `exp`, `ln`, `pow` and the rest are software functions from `libm` with no default features (no arch-specific paths), wrapped in `num`. They give the same bits on every platform.
- **Trig fidelity for built-ins.** GM8 runs on the x87 FPU, whose FSIN and FCOS differ from libm. The kid's gravity uses `gravity_direction` trig, and the drift this causes is a real trick (the "28 second trick", `research/knowledge/physics-core.md`). The traces already show it: with `gravity_direction = 270` and gravity 0.4, the kid's hspeed becomes `-7.347880794884119e-17` (`research/specs/engines/gm8/traces/rely-the-needle-4-2/djump.csv`). That trace was recorded under OpenGMK, which uses plain f64. The real runner differs in the last bits: it uses x87 FCOS/FSIN, and the standing kid's hspeed there is `-7.347638122934264e-17` (`research/specs/engines/gm8/traces/rely-the-needle-4-2/real-fpu-trig.real.txt`; `research/specs/engines/gm8/CLONE_SPEC.md`, Number handling, Confirmed (real runner); `research/docs/real-runner.md`). The difference is about 2e-21 absolute, far below the comparison tolerance, and every golden is a recorder trace, so by decision (research#8) the client keeps the recorder's libm bits. So:
  - `num::dsin` and `num::dcos` check a small table of exact bit patterns for the angles built-ins use (0, 90, 180, 270 and any others found), and use libm for every other angle.
  - Each table entry records where its value came from: an OpenGMK trace, or a measurement on the real GM8 runner.
  - Answered (real runner, research#8): the real runner's bits differ from libm's in the last place, and the table keeps the recorder's value by decision. Still **OPEN** on the real runner: `atan2` and non-axis angles (research#154); that matters only for bit-exact replay against the real runner. Scripts use plain libm trig, because bullets do not need x87 parity.
- **No x87 fallback needed.** Confirmed (real runner, research#8): the game thread runs at x87 53-bit precision with round to nearest (control word 0x1272), so `+ - * /` give binary64 results; a full jump's 42 airborne y values equal the recorder's bit for bit (`research/specs/engines/gm8/traces/rely-the-needle-4-2/real-key-repeat.real.txt`, `research/docs/real-runner.md`). The idea of a `rustc_apfloat` X87DoubleExtended model behind `float_model = "x87_ext"` stays unbuilt; `NumRules::float_model` holds only `f64` (N3).
- **Literals.** Constants in Rust are decimal literals, which Rust rounds correctly, or `from_bits` when a trace demands it. Data files may write `{ bits = "..." }` for the same reason. GML decimal literals are not always the nearest double: the recorder reads them as all digits as one integer times the double nearest 10^-k, so `0.95` is 0.9500000000000001 (N14, research#104; `num::gml_literal`). The converter applies that model and writes the resulting double in shortest round-trip form, so the sim and the script engine only ever parse decimals correctly rounded; a Rust constant that ports a GML literal holds the recorder value (ice `temp_decay`, the GAMEOVER overlay cap). Because the model lives in converted data rather than in `NumRules`, a differing answer would mean re-converting the affected literals and re-pinning, not a new `engine_rev`. The real runner parses literals the same way (CLONE_SPEC, Number handling, Confirmed (real runner), research#8), so N14 stands against the original too.
- **Rules, not constants.** Every number rule with OpenGMK provenance or an open spec status (compare epsilon, truthiness, `sign`, `min`/`max` ties, signed zeros, alarm and byte conversions, `string()` rounding, float model) is a field of `NumRules` in `RunnerRules`, never a `const`, so a rule settled later becomes a new `engine_rev` (plan section 3.2).
- **NaN and infinity** (plan 10.2, N15). `Real`'s `Eq` compares raw bits, and NaN payloads and signs differ between x86_64, wasmtime and browser engines. So every `Motion`, `Image`, alarm, view and variable setter, called from a built-in or a script, rejects a non-finite value with `SimError::NonFinite`, which halts the sim. Intermediate non-finite values inside one `num` function are allowed only if the function's result is finite. The state hash also maps every NaN to one bit pattern.
- **Motion coupling.** As in GM8, setting `hspeed` or `vspeed` recomputes `speed` and `direction`, and setting `speed` or `direction` recomputes `hspeed` and `vspeed`. The trace shows this: `speed = 7.347880794884119e-17`, `direction = 180` once vspeed is 0. Details (the 0.0001 snap, direction wrap) come from the CLONE_SPEC.
